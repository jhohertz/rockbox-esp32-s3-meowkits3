on 2026-11-04. This is the third packaged build of the port and it supersedes
[`esp32-s3-idf-20261029`](../esp32-s3-idf-20261029/release-notes.md). Its reason for
existing is one bug: **the two earlier builds displayed nothing on a board's first
power-on.** Everything else here is supporting work.

This is not an official Rockbox release. It is a working fork meant to be merged
upstream: core files carry only weak seams that leave every other target's behaviour
untouched. `README.md` (copied into this folder) describes the port itself.

## The bug, and why it took three releases to see it

A virgin board — one that had never run this firmware — showed a flicker and then a
dark screen on a cold power-on, while every reset button press looked normal. The cause
is ordering rather than programming. `lcd_init_device()` brings the AXP173's rails up
because `apps/main.c` reaches the display before `power_init()`, and it then
immediately addresses the PCA9557 I²C expander and pulses the panel's reset. Both
devices hang off rails that were only just commanded up, and neither reports an error
while its power-on ramp is still running; the writes are simply discarded. One second
of settle between the two makes the init land.

The reason no earlier observation caught it is that **a chip reset does not reset the
ST7789.** Its bias, gamma, colour format, rotation, inversion and display-on settings
survive a reset, so after the first boot the panel is already configured and only the
pixel writes matter. Every warm boot therefore looked correct. A rails-off power-on is
the only case that exercises init, and it had never been performed on a board running
our firmware.

Two consequences worth stating plainly: users of the two published builds hit a dark
screen when they first plugged in, and the fix is a one-line delay, not a rewrite. The
panel driver, its reverse-engineered controller rules, the pixel byte order and the
window pairing were all verified along the way and are unchanged — replacing the
hand-rolled SPI path with ESP-IDF's `esp_lcd` was tried and made things worse, so it
was reverted.

## Flashing

Unchanged from the previous build. `rockbox-flash.bin` goes at `0x0`:

- **Web installer:** <https://esptool.spacehuhn.com/>, hold BOOT through the hole on the
  back, tap RESET, flash, then power-cycle.
- **Command line:** `esptool.py --chip esp32s3 --port /dev/ttyACM0 --before default_reset
  --after no_reset -b 115200 write_flash 0x0 rockbox-flash.bin`. 115200 rather than the
  default 921600, because this board's USB-Serial-JTAG link drops handshakes at the higher
  rate.

**Power-cycle afterwards.** The download latch survives a reset, so a board flashed this
way stays in the loader until it is powered off and back on. Holding BOOT while plugging
in is the reliable way in, and unplugging is not a reset — the AXP173 keeps the chip
running on battery.

## SD card

FAT32, extract `rockbox.zip` into the root so it creates `/.rockbox`. **If the card came
from either earlier build, re-extract it.** The firmware rejects codec and plugin images
whose embedded target id differs from its own; that id is 134 here and was 126 in the
previous build, and the plugin API check is an exact match against 286. An old card
therefore plays nothing at all — silently for audio — and every plugin reports
"incompatible model".

## What changed since `esp32-s3-idf-20261029`

**Cold power-on displays correctly.** The settle delay above, verified on two units.

**Rail ordering for units that have never seen this firmware.** `meowkit3_board_init()`
raises LDO4 before anything touches the expander. LDO4 powers the PCA9557, and at its
reset default of 1200 mV the chip does not acknowledge its I²C address at all, so on a
virgin board the panel's reset and chip-select pins stayed inputs forever. Earlier builds
only worked because the AXP173 keeps its registers across an ESP32 reset — the rails were
already up from whatever had run before.

**Voice clips ship.** `english.voice`, 950 clips, 2.52 MB, generated with espeak-ng from
this target's feature list. `talk.c` was already compiled in earlier builds; what changed
is that the package now carries the clips, so the voice UI has something to play.

**The tree was rebased onto upstream `master`.** That brought upstream's new targets and
moved this target's identity numbers, which is what changed the target id and the plugin
API version. Core files remain byte-identical to upstream except for weak seams.

**Conformance cleanups with no behaviour change.** An `asm/memset16.c` special case for
Xtensa was removed after disassembly showed it produced identical code to upstream's own
size-optimised path; the target's optimisation level was confirmed to match every other
native target; and USB-driver placement moved into the shared driver where upstream
expects it.

**Board tooling.** `tools/meowkits3/rb-board-preserve` captures a board's entire shipped
state — 16 MB of flash, eFuse table, partition layout, MAC — before anything is written to
it, and `rb-board-restore` puts it back, refusing if the recorded checksums don't match.
This is how the virgin unit was made safe to flash.

## What is verified

On two MeowKit ESP32-S3 units, including one that had never run this firmware and whose
shipped state was captured first: cold power-on shows the UI, backlight, battery
percentage and touch response; audio playback; recording; USB mass storage, audio class
and the serial console; plugins including doom; the tick-driven behaviours — buttons,
backlight timeout, screen sleep — after their move into the target. Charging works and the
coulometer-backed percentage tracks a measured discharge within 4.3% of an independent
current integration.

## What is not verified

- **Runtime estimates.** No capacity run has completed, so there is no honest "N hours"
  figure. Current measurements are ~42 mA at dark idle and ~84 mA during playback.
- **The charge-termination signal.** The AXP173 has no charge-done flag; "full" is
  inferred from the current taper and has not been watched through a complete cycle.
- **Whether the board wires a thermistor to the PMU's TS pin.** The chip's charge and
  discharge suspend thresholds act on that voltage. The schematic shows none, but the
  shipping firmware drives it, so a floating input could suspend charging on a reading
  that means nothing.
- **Two long-standing items unchanged by this release:** a fetch-class panic captured
  twice with no reproduction, and the mpegplayer buffering thread occasionally failing to
  be created after a long chain of codec and plugin switches until a reboot.
- **Behaviour on a card larger than the directory cache.** 384 KB of directory cache was
  chosen by measurement against a 1-bit SD bus; a very large library may still thrash.

The artifacts in this directory were produced on the release host at the tagged commit,
and the image flashed to a device was read back and matched byte for byte.

The container recipe below builds the same tag successfully. Two things emerged from
running it. `tools/meowkits3/esp-layout-check` called gawk's `strtonum()`, which does not
exist in the container's mawk, so the layout guard reported "no executable segment" --
fixed, and verified to print identical figures under GNU awk 5.3.2 and mawk 1.3.4. And the
container's *baked* entrypoint script is a copy taken when the image was built, so an older
image runs an older packaging script regardless of what is mounted; run the container with
`--entrypoint /src/rockbox/tools/meowkits3/rb-build-artifacts.sh`, or rebuild the image.

A container build at the identical tag is not byte-identical to the host build. Same entry
point, same segment count, identical `.iram0.text`, `.dram0.data`, `.dram0.bss`,
`.ext_ram.bss` and sdkconfig, but the DROM segment differs by 176 bytes and the two data
segments are split differently. That is a build-environment difference still under
investigation, not a claim of bit-for-bit reproducibility; the shipped checksums are the
host artifacts, and the device image was verified against them.

## Reproducing this build

```sh
docker run --rm -v "$PWD:/src" -v "$PWD/build-out:/out" rb-meowkits3
```

or on a host, with the ESP-IDF environment sourced:

```sh
mkdir build-meowkits3 && cd build-meowkits3
../tools/configure --target=meowkit-esp32s3 --ram=8 --rbdir=/.rockbox                    --type=AV --language=english --tts=espeak
make && make voice && make zip && make espartifacts && make fontzip
```

ESP-IDF v5.5.5, xtensa-esp-elf 14.2.0, host GCC 15. `build-manifest.txt` records the
exact commit, and the version string embedded in the image is the same commit, so
`Debug → View HW info` on the device reports what you flashed.
